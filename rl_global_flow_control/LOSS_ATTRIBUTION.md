# 丢包归因表(Loss Attribution Table)

把两个 P4/BMv2 实验(16node 令牌桶版 + 全局调度版)中**实际遇到过的所有丢包现象**,按"丢在哪、突破哪项约束、根因、如何修复"归类。核心原则:

> **丢包不是"网络随机坏了",而是某个节点在处理速率 / 缓冲容量 / 链路带宽 / 协议正确性 四类约束里,有一项被需求突破了。**

## 一、丢包位置总览

一条路径上可能丢包的位置,及各自的约束:

```
h1 发送 → ① 交换机入口 → ② 交换机出口/队列 → ③ 接收内核(校验) → ④ 接收 socket 缓冲
            │              │                   │                  │
         处理速率约束    带宽/缓冲约束        校验正确性约束      缓冲容量约束
```

| 位置 | 所属节点 | 突破的约束 | 丢包时的典型症状 |
|---|---|---|---|
| ① 交换机入口 | 交换机 | 处理速率(CPU 每秒能处理的包数) | 输入端口 RX 大,转发出去很少 |
| ② 交换机出口/队列 | 交换机 | 链路带宽 / 队列缓冲容量 | 时延飙升 → 队列满 → 丢 |
| ③ 接收内核校验 | 接收主机 | 协议正确性(校验和/时序) | 网卡收到但 socket 收不到,InCsumErrors>0 |
| ④ 接收 socket 缓冲 | 接收主机 | 缓冲容量(应用没及时读) | RcvbufErrors>0 |
| ⑤(端到端)速率策略 | 发送/中间 | 策略设计(限速本意) | 丢包率符合设定的限速比例 |

## 二、两个实验中实际遇到的丢包(归因表)

| # | 实验现象 | 丢的位置 | 突破的约束 | 根因 | 修复 |
|---|---|---|---|---|---|
| 1 | 20 Mbps 打流,不限速也丢 | ① 交换机入口 | 处理速率 | `--log-console` 让 BMv2 逐包写日志,CPU 拖垮,处理不过来 | 去掉 `--log-console`;日志写文件 |
| 2 | RTT 从 90ms 涨到 500ms 再丢 | ② 出口队列 | 带宽/缓冲 | 出口速率 < 入口速率,队列积压 | 放低发送速率 / 调度器 pacing |
| 3 | UDP/TCP 全不通,只有 ping 通 | ③ 接收内核 | 校验正确性 | BMv2 转发改 TTL 后不重算 UDP 校验和,接收端 InCsumErrors 静默丢弃 | P4 里 `h.udp.checksum = 0` |
| 4 | 打高速流时偶发丢包 | ④ socket 缓冲 | 缓冲容量 | 应用来不及读,接收缓冲满 | 放低速率 / credit 流控 |
| 5 | h2 限速 8M 但 0% 丢包(限速没生效) | — | (配置) | rate 换算少除 8:8M 被配成 64M | `rate_bps / 8 / 1e6` |
| 6 | burst=800 < 包长,全丢 | ② meter | (配置) | 桶容量比单个包小,每个包都拿不够令牌 | burst ≥ 1500B |
| 7 | h2 限速 8M,15.7M 流 → 50% 丢 | ⑤ 速率策略 | 限速设计 | 超速部分被令牌桶有意丢弃(正常) | —(这是流量控制的正确结果) |
| 8 | h2→h1 首次 66% 丢(2 节点) | — | 启动时序 | BMv2 刚启动,数据面未就绪 | 加长启动等待 sleep |
| 9 | 全局调度版早期 5760 发只收 120 | ①+③ | 处理速率+配置 | ① 8 对并发超发压垮单线程 BMv2;② 监听端口错位只收到 1 个 listener | 修复端口对齐 + 调度器 pacing |
| 10 | 全局调度版最终 11840 发 11840 收 | 无 | 全部归零 | pacing 控制在交换机能力内 + 校验清零 + credit 防缓冲 | —(目标态:0% 丢包) |

## 三、约束条件与调优手段(映射表)

| 约束 | 突破后果 | 调优手段(在本次实验中) |
|---|---|---|
| 处理速率 | 入口丢包 | 去掉 log-console;调度器 pacing 把总速率压在交换机能力内 |
| 缓冲容量 | 队列/接收缓冲丢包 | 控制发送速率;credit 授信防超发;调 ECN 阈值提前标记 |
| 链路带宽 | 队列积压→丢 | 速率整形 / 调度器动态调速 |
| 协议正确性 | 静默丢弃 | P4 里清零 UDP 校验和;update_checksum 重算 IP 头校验 |

## 四、从"随机丢包"到"可归因丢包"——本实验的方法论

1. **定位位置**:按 ①②③④ 四个位置统计,判定丢包发生在哪。
2. **归因约束**:该位置的哪项约束被突破(处理/缓冲/带宽/校验)。
3. **修复约束**:要么降低对该约束的压力(降速、pacing、credit),要么修复配置让它不误丢(校验清零、burst 调大、rate 换算)。
4. **验证收敛**:修复后应只剩"策略性丢包"(限速/拥塞控制的正常结果),随机丢包为 0。

**最终结果**:全局调度版把四个位置的"无意丢包"全部消除,做到 **11840 发送 / 11840 接收 = 0% 丢包**,同时接收端 `InErrors / RcvbufErrors / InCsumErrors` 全部为 0——丢包从"随机现象"变成了"可归因、可优化、可解释"的工程指标。
